## Intent

**Problem:** Story 3.5 deliberately stopped at the one-way flag: "Under-review mechanics, pending-decision pauses and corrections are entry 7's, not this table's" (`migrations/024-assessment-item-flags.sql`). Today a flagged item only hides its flag button — no Under-review state exists, no pending completion decision pauses, no corrected replacement is offered, and the fresh-question surfaces (targeted retests) have no honest resource-delay path: nothing can exhaust, so "quota delays never record a failed attempt" is untested machinery nowhere.

**Approach:** Consume and extend the 3.5 flag into a two-state dispute machine (`under-review` → `corrected`) recorded in migration 026's `app.item_dispute`, opened ATOMICALLY by the existing flag verb (one dispute per flag row, insert-once — the flag verb's result shape and "changes no outcome" receipt contract stay byte-identical; the pause gates only FUTURE award INSERTS, never existing rows). The pause is a pure predicate (`disputes.ts`, the guidance.ts pattern) evaluated inside `evaluateAwardOnCourse`: while an OPEN dispute could affect the release's would-be satisfaction paths, the unearned award INSERT is skipped; earned awards are structurally untouchable (023's insert-once shape — no code path updates or deletes them, so "never revoked" is structural). The correction path is a **corrected replacement**: a dispute-scoped fresh assessment of the disputed item's whole objective group, mirrored one-for-one from the ROOT attempt's blueprint (same per-item points, root pass mark/rubric pinned — the `buildRetestSnapshot` comparability rules) but drawn from a NEW manually checked replacement pool (D7), so a learner who has seen the root and retest pools never meets a repeat question. A clearing replacement resolves the dispute `corrected` (defect annotated on the dispute row — attempt rows stay immutable), satisfies the disputed group in the same predicate `recoverySatisfied`/completion already use (additively: cleared-by-retest OR corrected), and un-pauses the decision — satisfying the requirement WITHOUT an extra ordinary attempt ever being started. A non-clearing replacement grades honestly and records NOTHING as a failed attempt; the dispute stays under review and retries are unlimited. The honest resource-delay path: a deliberately bounded local daily budget for fresh-question generation (retest + replacement starts — ordinary retakes reuse the fixed root bank and are never limited or counted), enforced by an atomic upsert-increment in `app.assessment_generation_use`; exhaustion fails `RATE_LIMITED` BEFORE any insert inside the fenced transaction, so a denied start records zero attempt/retest/replacement rows anywhere — the rollback IS the "no failed attempt" guarantee (AD-9 idempotence: the command-envelope replay returns before the counter, so a replayed start never double-counts).

## Boundaries & Constraints

**Always:**
- The dispute opens in the SAME transaction as the flag (one row per flag, `ON CONFLICT (flag_id) DO NOTHING`); flag replays and repeat flags stay exactly-once; the flag verb's result/receipt and 3.5's "scores, ledger, awards byte-identical before and after" contract hold — the pause only gates future award INSERTS on the disputed release.
- Pause predicate (pure, unit-covered): the unearned completion decision of release C pauses while an OPEN dispute could affect it — i.e. while NO untainted satisfaction path exists: no final graded PASSING attempt on C free of open attempt-item disputes, and no graded-FAILED attempt on C whose ledger is fully cleared-or-corrected with its chain (the attempt and its retests) free of open disputes. Resolved (corrected) disputes never pause; disputes on other releases never pause C; earned awards are never touched by any of this (C6: only pending/unearned decisions pause).
- Earned-pass protection: a previously earned pass row and any earned award row are never updated, deleted or re-derived by dispute machinery — protection is structural (no revoke path exists), and the served completion state still derives from award rows only.
- The corrected replacement mirrors the ROOT attempt's items for the disputed item's objective group one-for-one (same points, positions renumbered, root pass mark/answer rule/rubric/override pinned), uses ONLY the new replacement pool (fresh prompts — distinct from both existing pools), grades by the same integer cross-product (`groupResultsOf`/`groupCleared`), and withholds answers until its own submission (pre-grade views carry no answerId — same schema-level fence).
- A clearing replacement: resolves the dispute `corrected` (status-guarded, records which replacement and when — the defect annotation lives on the dispute row, never on the immutable evidence), counts as corrected coverage in the requirement predicate, and runs the award evaluation in the SAME transaction (the contributing-verb pattern). A non-clearing replacement: grades, lists in history, records NO failed attempt anywhere (it is not an ordinary attempt; the ordinary attempt count is unchanged), dispute stays `under-review`, retry unlimited.
- `recoverySatisfied` semantics extend additively to cleared-OR-corrected so the served recovery panel, the award predicate and the roadmap can never disagree; with zero disputes the predicate is byte-identical to 3.2's (every existing test path unchanged).
- Quota honesty: one deliberately bounded daily budget for fresh-question generation (retest + replacement starts), a module constant named in the served state and the denial message — the surface states the limit and the reset, never promises unlimited free generation; ordinary attempts/retests/replacements are never limited for pedagogical reasons; the counter increments exactly once per committed NEW start (replay-first ordering), a denied start fails inside the transaction (full rollback — zero rows), and saved work (open attempts/retests, in-form answers, listed history) is untouched.
- Every new verb runs the full fence (identify → authorize → scopedRoot → expected-revision → replay → validation → write → content-free receipt) in ONE transaction (AD-2); receipts are content-free; cross-owner/stale/out-of-range denials follow the existing taxonomy with no leak.
- `npm run lint`, `typecheck`, `typecheck:worker`, `boundaries`, full unit suite green; integration suite AUTHORED to the project's conventions but NOT RUN this phase (the shared DB cluster is reserved for the sibling 3.6 lane — the orchestrator merges and runs it later); migration 026 is this story's only SQL and the module's only new tables.

**Never:**
- No revocation, rewriting or re-grading of any attempt, retest, ledger row, flag or award (AD-5 immutability — the dispute/annotation/replacement are NEW rows); no AI dispatch, provider reads or queue changes (the replacement pool is manually authored synthetic fixture, the 017/019/021/024 precedent); no instructor adjudication surface (epic 5's — personal study's only correction channel is the documented replacement, never an unchecked appeal that awards a pass); no withdrawal machinery for published items (instructor-course D4 machinery; nothing in this build can mark an item withdrawn, so "withdrawn items unusable for new attempts" has nothing to act on — recorded, not improvised); no editing `tests/unit/assessment.test.ts` or `tests/integration/assessment.test.ts` (sibling-lane collision rule — new test files only); no new dependencies, no lint-config changes, no refactor sweeps (3.10's job); no learner-facing time limits, no XP/locks; loopback-only, original synthetic fixtures only; migration numbers other than 026 are never created.

## Design Notes

Latitude taken (recorded per the house rule): (1) the dispute opens inside the 3.5 flag verb rather than a separate open-dispute verb — one flag IS one dispute (the UX pattern's "Disputed question — marked Under review"), the insert is conflict-no-op so 3.5's exactly-once contract is untouched, and the flag's served result keeps its shape; (2) pause precision is path-based rather than "any dispute on the release": a clean newer passing attempt escapes the pause because the decision rests on it — but a dispute on the passing attempt itself taints it, and a dispute on a failed attempt taints that attempt's whole recovery chain (its ledger and clears rest on the chain's items); (3) `recovery_target` rows are never mutated by corrections — the corrected coverage rides the dispute row and the additive predicate, so 022's CHECKs and the immutable ledger stay intact and the served panel/completion/roadmap read one shared predicate; (4) the replacement re-assesses the disputed item's WHOLE objective group (not just the item) — that is the same independent cross-product comparability the retest path uses, and it is what makes "corrected replacement satisfies the requirement" honest arithmetic rather than an appeal; (5) a non-clearing replacement does NOT resolve the dispute 'upheld' — personal study has no adjudicator, an auto-uphold would close the Under-review state on evidence the learner may still contest, and the one-way once-per-item flag could never reopen it; the honest states are under-review (retry unlimited) and corrected (a clearing replacement documented it); (6) the generation budget is a module constant (20/day, retests + replacements combined) rather than config-table machinery — it is a local synthetic-derivation budget, deliberately not dressed up as a service SLA; the counter's day is UTC (deterministic for tests; no learner-facing date math rides it); ordinary attempt starts are unlimited AND uncounted because they draw the fixed root bank (no fresh generation); (7) the pause gate sits on the award INSERT only — parent awards stay structurally paused (their evaluation runs only after a child award lands), so no separate parent-pause code exists; (8) `resolved_by_replacement`'s FK is added by the guarded DO-block after both tables exist (circular reference), the 015/016 precedent.

## Implementation Notes (D7 manual fixture check — replacement pool)

Every replacement item's correct choice is trivially, self-evidently true against D3's correction policy; every wrong choice self-evidently false. Per item (pool position → root points 1999/1999/1999/1999/2004):
1. A flagged scored item is marked Under review — correct: "The item is marked Under review while its validity is checked" (b); wrong variants claim the flag deletes the item, regrades the attempt, or awards the pass.
2. What a pending completion decision does while the disputed item is under review — correct: "It pauses until the dispute is resolved; evidence is retained" (b); wrong variants claim it revokes the earned award, awards completion anyway, or deletes prior attempts.
3. What happens to an ALREADY-EARNED pass when its item is found invalid — correct: "It stands — history preserved, the defect annotated" (b); wrong variants revoke, rewrite or average it.
4. What the corrected replacement must do — correct: "Re-assess the disputed coverage with fresh comparable questions at the same demand and mark — never count the dispute as another failure" (a); wrong variants count it as a failed attempt, lower the mark, or let an appeal award the pass.
5. What an exhausted generation quota does — correct: "Delays new generation with a clear message and saved work — never records a failed attempt and never promises unlimited free generation" (b); wrong variants record a failure, erase saved work, or promise unlimited generation.
