# Spine Pair Review — project-new

Reviewed 2026-10-21 against `bmad-ux` assets (mobile/shadcn/editorial DESIGN examples, mobile/shadcn EXPERIENCE examples) and `references/design-md-spec.md`. Subject: `DESIGN.md` (Fieldnotes) + `EXPERIENCE.md` (Fieldnotes). Sources verified: `../initiative-ai-learning-platform.md` (R1–R22), `.memlog.md`, `mockups/key-review-inbox.html`, `mockups/key-instructor-approvals.html`, epic-1 `setup-experience.md` (U0–U8), `product-policies.md` (D1–D8), and prototype stylesheets `src/app/globals.css` / `src/app/demo/demo.module.css`.

## Overall verdict

This is a strong, source-extractable spine pair: every R1–R22 requirement is accounted for in the coverage map with defensible rationale for the three non-flow requirements, all token references resolve, both mocks are linked inline and consistent with the tokens, and the measured WCAG contrast table exceeds the bar. Two medium findings need attention before story-dev leans on it hard: DESIGN.md never formalizes an input/field component despite form-heavy setup flows (the prototype styles inputs with a radius that matches no token), and R17's five activity-format families get one paragraph of behavior with no per-family pattern and no recorded deferral. Everything else is minor polish.

## 1. Flow coverage — strong

Extraction: R1–R22 from the ticket; five Key Flows (Wen, Kai ×2, Dr. Lam, Priya). Each flow has a named protagonist, numbered steps, an explicitly marked **Climax** beat. Failure beats present in Flows 1–3; Flows 4–5 embed their decline (Flow 4 *is* the refusal journey) and exhaustion (Flow 5 step 3) beats in-step, which satisfies "where applicable". Coverage map (EXPERIENCE.md line 208) accounts for all 22: 18 via flows; R2 via denial paths; R9/R17 via lesson shells/trackers; R19 as non-surface. The R19 claim is verbatim-supported by the ticket ("This is not a mandatory in-product 4D assessment feature") — holds. The R2-via-denial position holds on the strength of Flow 3's failure beat plus the two cross-access state rows, but see finding 1.1.

### Findings

- **Minor — R2's Flow 1 attribution is nominal.** The coverage map says R2 is "exercised as the denial paths in Flows 1/3", but Flow 1 contains no denial beat — only the private-ownership empty state (step 1). The actual learner-side denial evidence lives entirely in State Patterns ("Cross-owner / revoked access", "Forbidden / missing"); only the instructor-side denial is a flow beat (Flow 3). Location: EXPERIENCE.md Key Flows, coverage-map paragraph. *Fix:* either add one denial beat to Flow 1 (e.g., a second learner's direct link to Wen's upload → "This item is unavailable") or reword the map to "Flow 3 + the cross-access state rows".
- **Minor — R8's assignment to Flow 5 is by attribution, not demonstration.** R8's acceptance check is "suitable treatment of the same objective for a non-CS beginner and a CS graduate"; Flow 5 exercises R6/R11/R18. Background adaptation is only implicit in the Wen/Kai protagonist split — no beat shows the same objective treated differently. Location: EXPERIENCE.md coverage map; Flow 5. *Fix:* one clause in Flow 5 or Flow 1 noting the same objective rendering at Kai-depth vs Wen-depth, or reassign R8 to "protagonist split across Flows 1/2" in the map.
- **Medium — R17 activity families are one paragraph with no per-family pattern and no recorded deferral.** Simulation, role play/mock interview, mini-game, narrated animation/slides and online coding get a single honest-unavailable rule (Component Patterns closing paragraph). No behavioral pattern, no state beyond unavailable, no interaction contract for any family — and unlike the instructor shell, the deferral is not listed under Open Questions. Downstream (epic 6 story-dev) has nothing to build against and no signal that more is coming. Location: EXPERIENCE.md Component Patterns, "Activity-family shells" paragraph. *Fix:* either five short pattern rows (use, core loop, submission/evidence rule per family) or an explicit Open Questions entry deferring activity-family interaction design to epic 6 refinement.

## 2. Token completeness — strong

Extraction: 23 frontmatter colors (all kebab-case, all quoted hex — none missing); 12 typography entries (well-formed subsets of fontFamily/fontSize/fontSize/lineHeight/letterSpacing; `clamp()` and `em` values are legitimate CSS dimensions); 4 rounded; 11 spacing (named tokens are spec-allowed); 16 components with internal `{path.to.token}` references. Every `{…}` reference in both files' prose was checked and resolves. Contrast targets: a measured WCAG 2.2 table covering 15 load-bearing pairs, with the disabled 5.0:1 pair explicitly flagged exempt — exceeds the rubric's requirement. EXPERIENCE.md's Visual column references all resolve by name to DESIGN.md component tokens.

### Findings

- **Minor — one unresolved wildcard survives the earlier fix pass.** DESIGN.md Components → Buttons still reads "disabled uses the `{colors.disabled-*}` trio". `.memlog.md` records that wildcards were replaced with named tokens (Colors section, line 215, was fixed); this instance was missed. A token resolver cannot flatten `*`. Location: DESIGN.md line 245 (Components → Buttons). *Fix:* spell out `{colors.disabled-bg}`, `{colors.disabled-fg}`, `{colors.disabled-border}`.
- **Minor — custom rounded scale names (`pill`, `circle`) instead of the spec's canonical vocabulary.** The spec enumerates `sm/md/lg/xl/full/DEFAULT` (`full` conventionally `9999px`); Fieldnotes uses `pill: 2rem` and `circle: 50%`. Self-consistent and correctly referenced everywhere (mocks use `--r-pill` identically), so impact is low — but a consumer expecting the canonical scale will not find `rounded.full`. Location: DESIGN.md frontmatter `rounded`. *Fix:* either rename `pill`→`full` (2rem works as a badge radius) or keep and note the deviation once in Shapes ("`pill`/`circle` are this system's names for the conventional `full` and a glyph circle").

## 3. Component coverage — adequate

Extraction: 16 DESIGN.md components (frontmatter + Components section, names identical in both places); 16 EXPERIENCE.md Component Patterns rows, each with a Visual column resolving to DESIGN components, each with real multi-clause behavioral rules — not one-word rows. Composition via `{components.panel}` + `{components.pill}` etc. is legitimate and consistently used. Four components lack an EXPERIENCE patterns row (finding 3.2); one load-bearing control family is missing from DESIGN.md entirely (finding 3.1).

### Findings

- **Medium — no input/field component in DESIGN.md.** The product's core loop is forms — U2 acknowledgment checkbox, U4 goal routes, U5 plan editor, U3 consent Allow/Not now, CSV confirm — yet DESIGN.md Components has buttons, panels, pills and options but no text field, select, textarea, checkbox or file-input spec. The prototype styles all of these (`src/app/globals.css` 203–218: 1px `#89998e` border = `{colors.input-border}`, 0.2rem radius, 0.65rem padding, textarea 96px min-height + vertical resize), so the visual contract exists in code but was never formalized. Worse, the prototype's 0.2rem input radius matches **no** token (`rounded.sm` is 0.25rem) — exactly the prototype-vs-token conflict the spine exists to resolve, and nothing resolves it. Downstream implementers of the setup surfaces have color tokens but no visual contract for the most-used control. Location: DESIGN.md Components (absence); EXPERIENCE.md Plan editor / Consent panel rows ("form fields" is the only spec). *Fix:* add an `input` component (border `{colors.input-border}`, radius — decide 0.2rem-is-legacy vs `rounded.sm`, padding, min-height, focus via `{components.focus-ring}`, disabled trio) plus a choice-control note (checkbox/radio → answer-option styling or separate), and reference it from the affected EXPERIENCE rows' Visual column.
- **Minor — four DESIGN components have no EXPERIENCE Component Patterns row.** `button-lime` (is it product-reachable outside demo/sample mode, or demo-only chrome? unstated), `sample-badge` (its always-visible rule lives in Foundation's provenance invariant, not the patterns table), `feedback` (the post-submission block is implied by Recall card's withhold rule but never mapped — Recall card's Visual column omits `{components.feedback}`), `hero` (its at-most-one-per-view placement rule lives only in DESIGN.md). All recoverable from context; none blocks consumption. Location: EXPERIENCE.md Component Patterns (absences). *Fix:* one-line rows (or Visual-column additions) for feedback and sample-badge; a sentence stating button-lime's reachability; either a hero row or an explicit "placement rules are design-owned" note.

Instructor authoring-surface states are thin but the deferral is explicitly recorded (Open Questions, epic 5 unrefined) — acceptable.

### Findings

- **Minor — "Reminders paused" has no State Patterns row despite being a canonical mock state.** `mockups/key-review-inbox.html` column 2 specifies it precisely (list still renders, resume becomes primary, snooze disabled, no backlog burst on resume); the spine carries pieces of this in the Review row controls and the Review overdue row but never names the state. Location: EXPERIENCE.md State Patterns (absence); mock column 2. *Fix:* one row — "Reminders paused | Review inbox | Due list still renders honestly; resume is the single primary action; snooze disabled; resume sends no backlog burst (D6)."
- **Minor — approval-queue empty state unspecified.** The Empty surface row names Library, roadmap, review inbox and report; the instructor approvals queue (a surface whose empty case — nothing pending, all inspected — is common and healthy) has no treatment. Location: EXPERIENCE.md State Patterns → Empty surface. *Fix:* extend the row ("empty approval queue reads 'Nothing pending approval' — an inspected-all state, not an error").

## 6. Bloat & overspecification — strong

DESIGN.md prose carries editorial voice as the spec permits, and every section terminates in a decision (the Colors section is half contrast table). Component bullets reference tokens instead of restating values; no pixel specs exist that tokens don't cover (44px/64px are accessibility floors, not decoration). EXPERIENCE.md is almost entirely tables; its prose is confined to the Foundation invariants (load-bearing product law), Key Flows (canonical narrative form, with climax beats in the examples' register) and Decisions and Open Questions. Policy content is cited by R/D/U/C ID rather than restated wherever it is inherited; where it is restated (pass-mark display rules, snooze semantics) the restatement is the UI commitment itself, not ticket echo. No section is dead weight.

### Findings

- **Minor — "Decisions and Open Questions" partially duplicates `.memlog.md`.** Four of the five decided items (light-mode-only, English-only, no component library, lime/olive semantics) appear in both. The duplication is defensible — the memlog is a working log while the spine is the contract consumers read — but the two can drift when decisions change. Location: EXPERIENCE.md Decisions and Open Questions vs `.memlog.md`. *Fix:* none needed now; when a decision changes, update both in the same edit (treat the spine's list as the consumer-facing projection).
