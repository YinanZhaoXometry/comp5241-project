# Independent architecture rubric and initiative reconciliation

**Verdict: CHANGES REQUIRED before shared-contract handoff — 3 high and 3 medium findings; no critical finding.** The paradigm, operational envelope and most invariants are coherent, but course authorization granularity, deletion targeting and restore-time revocation need tighter shared rules. Mechanical integrity passes. No finding is evidence of an implemented vulnerability: this is a planning-only workspace.

## Findings and dispositions

### F1 — HIGH: Course scope does not define per-learner authorization

- **Evidence:** [AD-3](../architecture-shared-technical.md#L60-L64) defines `personal(ownerUserId)` and `course(courseId)`, current sessions, course ownership and enrollment. [AD-7/AD-8](../architecture-shared-technical.md#L86-L98) put an actor on evidence and prohibit learner-supplied scores, but do not require a learner's attempt/conversation/review resource to belong to that learner. [AD-14](../architecture-shared-technical.md#L134-L138) scopes instructor reports; it is not an access rule for every learner-facing endpoint. [D5](../../product-policies.md#L56-L68) additionally forbids exposing rosters to learners and allows removed learners to export their own progress/scores.
- **Trigger:** two learners are enrolled in the same course. One requests or submits the other's attempt, evidence, private course conversation or review state by ID. A repository that checks course scope and active enrollment satisfies the explicit coarse predicate but lacks the beneficiary/actor restriction. Conversely, a blanket enrollment requirement can deny the explicitly permitted own-history export after removal.
- **Consequence:** independent builders can implement incompatible permissions, including same-course peer disclosure or mutation. The named course scope alone cannot prevent this; opaque IDs and instructor-report filters do not repair it.
- **Smallest resolution:** extend `AD-3` with a compact resource/action access matrix: published approved content is enrollment-readable; roster, drafts and management are owner-instructor-only; learner attempts, conversations, evidence and review state are self-only unless an explicitly permitted instructor action applies. Require scope **and** subject ownership in repository predicates. Explicitly permit authenticated self-only progress/score export after enrollment removal, without permitting course-content/bank access. A shared rule/matrix is sufficient; no endpoint catalogue is needed.
- **Verification:** two enrolled learners cannot read/mutate each other's resources or enumerate the roster; the course owner can perform permitted grading/reporting; a removed learner gets only their own retained progress/score export and no restricted questions, other learners' data or new course activity.
- **Disposition / owner:** **discuss and resolve before handoff**; Identity/access owns the shared policy, consumed by Assessment/progress, Learning/content, Review and Instructor/reporting. Not safely deferrable to independent route implementations.

### F2 — HIGH: Restore suppression covers deletion, not other protective revocations

- **Evidence:** [AD-3](../architecture-shared-technical.md#L60-L64) promises immediate revocation through live database checks and authorization epochs. [AD-4](../architecture-shared-technical.md#L66-L72) separately retains a **deletion** tombstone journal. [AD-17](../architecture-shared-technical.md#L153-L158) requires replaying those tombstones before traffic/jobs; it says nothing equivalent for session/role/enrollment revocation or withdrawn processing consent. `R4`, `R22` and `C4` require these protective boundaries to remain effective.
- **Trigger:** a backup precedes enrollment removal, consent withdrawal, session revocation or an instructor-capability revocation. After restore, deletion replay succeeds, but the restored database contains the old grant, old epoch and possibly queued external-processing work. A fresh database lookup now validates stale authority.
- **Consequence:** previously removed access or forbidden future processing can resume. Restoring a protective publication withdrawal can likewise lose the hold on new use. This is distinct from deleted data resurfacing and is not covered merely by checking the restored epoch.
- **Smallest resolution:** add one restore invariant to `AD-17`: service remains quarantined until post-snapshot protective authorization/consent/withdrawal state is reconciled from a source not rolled back with the backup, or affected grants are invalidated and explicitly revalidated. Invalidate restored sessions. Cover queued work and egress before enabling them, not only HTTP traffic. The bounded journal/reconciliation mechanism can remain a `G5` implementation choice under existing retention/minimization limits; do not mandate indefinite audit storage or event sourcing.
- **Verification:** snapshot, then revoke enrollment/session/instructor capability and withdraw processing consent; restore the snapshot and prove reads, mutations, reminders and queued egress remain denied. Also verify a post-snapshot protective content withdrawal cannot reopen new use without reconciliation. Exercise this together with deletion replay, rather than treating a normal restore drill as sufficient.
- **Disposition / owner:** **discuss and resolve the invariant before handoff**; Lifecycle/platform and Identity/access own it, with Publication and provider-policy consumers. Implementation proof belongs to `G5` before real-data activation.

### F3 — HIGH: Deleting one material is conflated with tombstoning the entire personal scope

- **Evidence:** [AD-3](../architecture-shared-technical.md#L60-L64) identifies personal authorization scope as `personal(ownerUserId)`. [AD-4](../architecture-shared-technical.md#L66-L72) says personal **material** deletion includes its derivatives, then prescribes “deletion transaction tombstones the scope” and advances “its generation.” [D5 owner controls](../../product-policies.md#L63-L65) support deletion of personal materials and associated derivatives, not forced loss of every unrelated study root.
- **Trigger:** one learner has independent materials A and B and chooses to delete A. Tombstoning the only defined personal scope revokes B as well. An implementer instead inventing a per-material scope changes the shared authorization/deletion vocabulary; a single scalar generation is also ambiguous for a derivative that depends on both A and B.
- **Consequence:** either unrelated study data is revoked/purged, or independent modules implement incompatible deletion and late-result fences. The derivative registry lists lineage but does not settle the deletion target or fence identity.
- **Smallest resolution:** distinguish the immutable **authorization scope** from a **deletion target/root and its lineage fence**. Material deletion revokes the selected root and every dependent artifact, including multi-parent derivatives, while preserving unrelated roots. Whole-account/personal-scope deletion remains a separate operation. Jobs/results must check all relevant ancestor fences; an implementation cannot choose a weaker scope-only check. Keep the physical representation deferred.
- **Verification:** with independent A/B and a generated artifact C depending on both, delete A: A/C become immediately unusable and are purged on schedule, B remains usable, and a late A/C job cannot recommit. Separately prove whole-personal deletion affects all personal roots without deleting instructor-controlled records.
- **Disposition / owner:** **discuss and resolve before handoff**; Lifecycle/platform owns the target/fence contract, Materials/setup and every derivative-producing module implement it. This is not merely a deferred table/index choice.

### F4 — MEDIUM: Parent path/course completion has no explicit shared aggregate contract

- **Evidence:** [R13/R20](../../initiative-ai-learning-platform.md#L36-L43) and [D1](../../product-policies.md#L14-L22) require every required mini-course before its parent completes, whole-mini-course roadmap nodes and separate review indicators. [AD-5/AD-8](../architecture-shared-technical.md#L74-L98) define mini-course release manifests and version-scoped mini-course awards, not a parent required-child manifest/aggregation rule. The structural seed is explicitly incomplete, so the omitted diagram entity alone is **not** the finding.
- **Trigger:** Materials/setup creates a personal plan, Instructor owns course metadata and Assessment/progress supplies child awards. They independently choose whether a parent is complete when any child passes, all currently visible children pass, or all originally required child releases pass. Editing the plan or switching a child release exposes the difference.
- **Consequence:** the roadmap and instructor report can disagree, or a parent can appear complete with required children unfinished. The source requirement remains binding, but the cross-module representation and single decision owner are not settled.
- **Smallest resolution:** briefly extend `AD-5/AD-8`: identify the versioned parent requirement set of child release IDs; Assessment/progress alone evaluates parent completion from its required child awards, with review/access indicators kept separate. Declare how explicit plan/release changes select a new requirement version without revoking an earned version-scoped award. Carry the inherited no-hard-lock/whole-mini-course node policy into the shared progress query contract by reference to `D1`.
- **Verification:** required child incomplete, optional child incomplete, all required children complete, later review failure, child-release switch and parent-plan edit; learner roadmap and instructor report agree for the same parent version.
- **Disposition / owner:** **resolve before consuming refinement**, not a reason to enlarge the full schema now; Assessment/progress with Materials/setup and Instructor contract consumers.

### F5 — MEDIUM: Review success lacks a binding evaluation-policy handoff

- **Evidence:** [D6 adaptation](../../product-policies.md#L72-L75) says review uses the applicable pass mark. [AD-13](../architecture-shared-technical.md#L127-L132) defines calendar intervals after “successful unaided reviews” but not who produces that success or which policy version applies. `AD-7` deliberately separates review from scored-assessment purpose, and [AD-8's binds and snapshot rule](../architecture-shared-technical.md#L92-L98) do not explicitly close this review-consumer seam.
- **Trigger:** the review worker treats answered questions, a fixed local cutoff or an AI “success” label as success, while Assessment/progress uses the applicable disclosed threshold and possibly a provisional grade. A course threshold changes between completion and a later review.
- **Consequence:** equivalent evidence advances intervals differently across modules, or an unconfirmed subjective judgment extends a schedule. Completion remains protected by `AD-8`, so this is not an earned-completion revocation defect.
- **Smallest resolution:** make Review consume a server-authoritative review-purpose verdict from the shared assessment evaluator under an explicitly selected, snapshotted applicable release/policy; declare treatment of provisional instructor grades. No provisional or assisted result advances the success sequence. Preserve `AD-6` for any newly generated instructor-review content and keep review incapable of awarding/revoking completion.
- **Verification:** below/equal/above threshold, a non-default instructor threshold, a policy edit after review start, assistance and provisional/final subjective grades. The same verdict produces the same persisted next interval on retry.
- **Disposition / owner:** **resolve before the Assessment/progress → Review handoff**; these modules agree the small verdict/policy contract. Scheduler implementation and harness selection stay deferred.

### F6 — MEDIUM: Full generation is not bound to an exact confirmed plan revision

- **Evidence:** [R1/R21](../../initiative-ai-learning-platform.md#L24-L45) and [D2 plan confirmation](../../product-policies.md#L24-L31) require editable setup and confirmation before full generation. [AD-7](../architecture-shared-technical.md#L86-L90) places the diagnostic on a confirmed plan, but the generation boundary does not require a confirmation token/revision. Expected revisions in `AD-2/AD-15` are generic concurrency controls, not proof of plan confirmation; the capability map names the feature without closing this seam.
- **Trigger:** setup confirms plan revision P1, the learner corrects it to unconfirmed P2, and a queued generation handler reads “the latest plan.” Alternatively, a direct HTTP/job call bypasses the UI confirmation screen. Workers and web can choose different plans while each uses an expected revision correctly.
- **Consequence:** generation uses unconfirmed or silently changed objectives, source coverage or goals. This is an upstream setup/downstream-generation integration defect, not a request for more onboarding UI detail.
- **Smallest resolution:** require full-generation commands to reference an authorized immutable confirmed plan revision and selected source revisions. Edits require a new confirmation; queued work cannot silently substitute another revision. Define stale/canceled work as an explicit conflict/pending outcome with saved input. The 3–5-question diagnostic remains skippable and cannot exempt required work.
- **Verification:** corrected-plan confirmation, skipped diagnostic, direct generation without confirmation, edit-after-enqueue, duplicate command and stale plan/source references; no job generates against an unconfirmed substituted plan.
- **Disposition / owner:** **resolve before setup/generation integration stories**; Materials/setup owns confirmation, Learning/content consumes it. Add a compact contract clause, not a new planning document.
