## Source-fit follow-up

### SF-1 — Resolved by the explicit TypeScript 6 selection

- **Current contract:** the [compiler-selection evidence](../source-checks.md#L29-L30) selects TypeScript 6.0.3 rather than the observed latest 7.0.2. The spine's [Stack](../architecture-shared-technical.md#stack) agrees, explicitly excludes a dual compiler, peer overrides and lint suppressions, and its [G1 gate](../architecture-shared-technical.md#deferred) requires compilation and lint together.
- **Publication evidence:** the [exact TypeScript 6.0.3 registry endpoint](https://registry.npmjs.org/typescript/6.0.3) returned HTTP 200 and `version: 6.0.3`. Its integrity-checked archive contains the JavaScript compiler implementation, API declarations and `tsc` launcher. This is not a nonexistent version or the native TypeScript 7 package under another name.
- **Support evidence:** the [official typescript-eslint support policy](https://typescript-eslint.io/users/dependency-versions/#typescript) states `>=4.8.4 <6.1.0`. Both [typescript-eslint 8.72.0](https://registry.npmjs.org/typescript-eslint/8.72.0) and [parser 8.72.0](https://registry.npmjs.org/@typescript-eslint/parser/8.72.0) independently returned HTTP 200 and that same TypeScript peer range. TypeScript 6.0.3 falls inside it. [eslint-config-next 16.4.2](https://registry.npmjs.org/eslint-config-next/16.4.2) declares `typescript-eslint: ^8.56.0`, which admits the observed 8.72.0; that observation does not freeze future transitive resolution.
- **Reason for the change:** Microsoft's [TypeScript 7 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6-0) explicitly says 7.0 does not ship a compiler API and names typescript-eslint among tools needing TypeScript 6 programmatic access. The original finding allowed an explicit compiler revision as an alternative to a side-by-side arrangement; the current contract chooses that alternative without removing ESLint.
- **Disposition:** close SF-1. Retain G1: supported ranges, publication and an API-bearing archive do not prove the eventual Next/auth/worker/ESLint lockfile compiles and lints. No installation or compatibility result is implied.

### SF-2 — Resolved by deferred POST session refresh

- **Current contract:** the [Better Auth evidence row](../source-checks.md#L22) now states the default GET database-write behavior and selects `deferSessionRefresh: true`. The spine's [AD-3](../architecture-shared-technical.md#ad-3--identity-is-not-resource-authorization-adopted-d5-assumption-mechanism) requires that setting, disabled cookie caching, server validation and a POST refresh path for client/server-rendered journeys; AD-15 retains the no-GET-mutations rule.
- **Official documentation:** [Better Auth — Defer Session Refresh](https://www.better-auth.com/docs/concepts/session-management#defer-session-refresh) places `deferSessionRefresh: true` inside `session`. It explicitly describes default database writes on `GET /get-session`, a read-only GET with `needsRefresh: true` when enabled, and client POST refresh. This is not the different `disableSessionRefresh` option.
- **Selected-version evidence:** the [Better Auth 1.7.12 registry endpoint](https://registry.npmjs.org/better-auth/1.7.12) returned HTTP 200. The integrity-checked published implementation accepts GET and POST, reads `session.deferSessionRefresh`, returns the deferred-refresh indicator on GET, and guards expired-session database deletion so it is deferred to POST when enabled. This independently corroborates the current documentation for the selected version.
- **Integration boundary:** [official Next integration](https://www.better-auth.com/docs/integrations/next) exposes GET and POST handlers, documents server session validation and explains that React Server Components cannot set cookies. The architecture does not claim that a server-rendered GET refreshes itself: the required POST journey remains implementation and test work. Disabled cookie caching and subject/action authorization remain separate requirements.
- **Disposition:** close SF-2. Preserve auth revocation and POST-refresh tests at G1; source-fit closure is not a claim that those journeys already work.
