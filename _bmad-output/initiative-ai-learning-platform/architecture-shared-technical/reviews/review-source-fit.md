## Findings

### SF-1 — TypeScript 7 requires a deliberate compatibility arrangement for the selected ESLint starter

- **Location:** [Stack and official-starter contract](../architecture-shared-technical.md#L181-L195), [G1](../architecture-shared-technical.md#L280) and [registry evidence](../source-checks.md#L29).
- **Trigger condition:** installing native `typescript@7.0.2` as the sole package named `typescript` while retaining the official starter's TypeScript ESLint configuration is a known tooling mismatch, not just an unknown compilation result. G1 names framework/auth/worker compilation but omits this specific lint-tool compatibility issue.
- **Official evidence:** Microsoft's [TypeScript 7 announcement — side-by-side operation](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6-0) states that 7.0 does not ship a compiler API and specifically identifies typescript-eslint as requiring the 6.0 compatibility API. The [typescript-eslint support policy](https://typescript-eslint.io/users/dependency-versions/#typescript) currently supports `>=4.8.4 <6.1.0`.
- **Exact-version evidence:** the integrity-checked [create-next-app 16.4.2 archive](https://registry.npmjs.org/create-next-app/-/create-next-app-16.4.2.tgz) includes both `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript` in its TypeScript/Tailwind template. [eslint-config-next 16.4.2 metadata](https://registry.npmjs.org/eslint-config-next/16.4.2) depends on `typescript-eslint@^8.56.0`; [current typescript-eslint 8.72.0](https://registry.npmjs.org/typescript-eslint/8.72.0) and [parser 8.72.0](https://registry.npmjs.org/@typescript-eslint/parser/8.72.0) declare the same `<6.1.0` TypeScript ceiling. Broad top-level Next/Better Auth peers do not override this constraint.
- **Guard / correction:** record an explicit TS7 CLI / TS6 compiler-API compatibility arrangement, following Microsoft's documented aliases, and pin the resulting ancillary packages at scaffold; alternatively revise the compiler choice by an explicit architecture decision. Keep the intended ESLint checks and add lint compatibility to G1. Do not use peer-dependency overrides, disabled rules or successful Next compilation as a substitute.
- **Potential consequence:** an otherwise buildable scaffold has unsupported or failing lint installation/execution, or silently acquires a different compiler arrangement than the stack table implies.
- **Important distinction:** this is not a claim that Next 16 cannot build with TS7. The [current official Next TypeScript reference](https://nextjs.org/docs/app/api-reference/config/typescript#using-typescript-7) explicitly supports the project-local `tsc` CLI path. The mismatch is the selected lint toolchain's compiler-API dependency.

### SF-2 — Better Auth's default session GET writes conflict with the literal no-GET-mutations contract

- **Location:** [AD-15](../architecture-shared-technical.md#L140-L144) and [Better Auth source-fit row](../source-checks.md#L22).
- **Trigger condition:** disabling cookie caching, as required, does not make session reads read-only. Better Auth's default `GET /get-session` refreshes database sessions when due; it can also delete an expired session. The source-fit row identifies the cache setting but not the setting needed to reconcile these writes with AD-15's unqualified “No GET mutations.”
- **Official evidence:** [Better Auth — defer session refresh](https://www.better-auth.com/docs/concepts/session-management#defer-session-refresh) explicitly says GET performs database writes by default and documents `session.deferSessionRefresh: true`: GET becomes read-only, returns `needsRefresh`, and the client refreshes via POST. This behavior was also confirmed in the integrity-checked [Better Auth 1.7.12 archive](https://registry.npmjs.org/better-auth/-/better-auth-1.7.12.tgz): expired-session deletion and the deferred-refresh branch both distinguish GET from POST when this option is enabled.
- **Guard / correction:** make deferred POST refresh part of the auth-adapter contract while retaining database validation and disabled cookie caching; include the POST refresh path for server-rendered journeys. Alternatively explicitly scope AD-15 to business commands and document an intentional session-housekeeping exception. No change to authorization or retention policy is necessary.
- **Potential consequence:** the planned adapter violates its literal HTTP mutation rule, or implementers discover the exception only after assuming fresh session lookup is a read-only operation.
- **Scope qualification:** this is a documented default/contract mismatch, not evidence that the platform already has an exploitable GET endpoint or that cookie-cache disabling is wrong.

## Official-starter assumptions and configuration consequences

- **Supported selections:** TypeScript, App Router, ESLint, Tailwind, Turbopack, an import alias and an explicit source directory are all current documented choices. React Compiler is not enabled in recommended defaults. Next 16 `next build` no longer lints, so AD-18's separate lint gate is correct.
- **Cache Components requires an explicit opt-out:** the [current CLI reference](https://nextjs.org/docs/app/api-reference/cli/create-next-app#reference) enables Cache Components by default for App Router; recommended defaults also omit a source directory. The architecture already expressly selects the opposite for both, so this is not an architecture contradiction. Scaffold must explicitly select no Cache Components and a source directory rather than equating `--yes` with this contract; saved preferences can affect `--yes`. No fabricated “Cache Components off by default” claim is accepted.
- **Additional starter choices:** the current CLI also offers agent guidance/feedback settings. Record those decisions rather than allowing saved preferences to create implicit telemetry/feedback authority. Their existence does not demonstrate private-data egress or failure of AD-10.
- **React scope:** official installation docs distinguish App Router's bundled React canary from declared `react`/`react-dom` packages used for ecosystem compatibility. The table's stable pins are real packages, not a claim that every Next internal React component uses that exact stable implementation.
- **Private media:** the [official Image reference](https://nextjs.org/docs/app/api-reference/components/image#src) says the default optimizer does not forward authentication headers and maintains an image cache. AD-3's authenticated, non-shared-cached streaming boundary must also cover image rendering, e.g. unoptimized authenticated sources rather than public/presigned optimizer workarounds. No optimizer choice is committed yet; this is a source-fit implementation constraint, not an existing defect.

## Provider deletion gate: no false compliance claim found

- **Standard API remains blocked:** [Anthropic commercial retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) documents ordinary deletion within 30 days, longer-retained features and legal/misuse exceptions; flagged content up to two years, classification scores up to seven years and feedback five years. This does not satisfy the platform's seven-day active-copy rule merely because backups have a thirty-day ceiling.
- **ZDR remains conditional:** the [official ZDR article](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-products-does-it-apply-to) confirms organization-specific approval, eligible APIs and continuing legal/misuse/classifier exceptions. The linked [Covered Models retention policy](https://privacy.claude.com/en/articles/15425996-data-retention-practices-for-covered-models), readable in this review, adds a concrete model-specific reason to reject blanket ZDR assumptions: covered-model prompts/outputs generally require thirty-day retention, with stated eligibility qualifications. No covered model is selected by this report.
- **No-training is distinct:** [commercial training policy](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training) confirms no-training by default, but explicit feedback/bug submissions can change treatment. AD-10 correctly does not equate that default with deletion compliance.
- **Access limitation preserved:** the [platform ZDR reference](https://platform.claude.com/docs/en/build-with-claude/zero-data-retention) again redirected to an unavailable-in-region page. No exact model ID, snapshot, feature eligibility, SDK or organization agreement is therefore approved. The architecture's lack of an external model commitment is intentional and accurately gated, not a missing version invented into a finding.
- **SDK exclusion:** the observed Anthropic SDK 0.135.0 is explicitly excluded from the committed stack; no re-pin is required for an unselected package. SDK installation could not clear G2 in any event.
