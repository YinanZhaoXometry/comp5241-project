## Findings

### SEC-01 — Restore suppression covers deletion, but not other security revocations

- **Location:** [AD-3 current sessions/enrollment/epochs](../architecture-shared-technical.md#L60-L64), [AD-4 independent tombstone journal](../architecture-shared-technical.md#L66-L72), [AD-17 restore startup](../architecture-shared-technical.md#L153-L158), [AD-10 consent](../architecture-shared-technical.md#L106-L111).
- **Trigger condition:** Restore predates session revocation, enrollment removal or consent withdrawal without any scope deletion.
- **Missing handling:** Sessions, authorization epochs, enrollments and consent are ordinary restored database state. The only independently retained replay mechanism named is a deletion tombstone journal. Fresh database checks can therefore validate yesterday's now-invalid permission. Replaying deletion tombstones alone does not cover a removed enrollment, revoked session, withdrawn processing consent or publication withdrawal that never deleted a scope.
- **Potential consequence:** Previously denied users or queued work can regain access or resume external processing after recovery, despite immediate-revocation promises. A stale approval/withdrawal state can also reopen content.
- **Minimum guard:** Extend the restore contract to recover current denial/security-revision state independently of the restored snapshot, or keep affected scopes/processing fail-closed pending authoritative reconciliation. Invalidate restored sessions before opening traffic; doing only that is insufficient for stale enrollments/consents after a fresh login. Reconcile publication withdrawals too. Keep the journal/checkpoint content-free, access-controlled and bounded to the actual restore horizon; no event-sourcing redesign is necessary.
- **Later gate evidence:** Under G5, restore a pre-revocation backup where no deletion occurred. Old cookies, removed enrollment, withdrawn consent, withdrawn content and old queued jobs must remain unusable before traffic/dispatch resumes.

### SEC-02 — Authorization scope and selective-deletion root are conflated

- **Location:** [AD-3 scope identities](../architecture-shared-technical.md#L60-L64), [AD-4 material deletion and scope generation](../architecture-shared-technical.md#L66-L72), [required multi-parent lineage](../architecture-shared-technical.md#L245), [D5 owner controls](../../product-policies.md#L63-L65).
- **Trigger condition:** One learner deletes material A while keeping unrelated material B in the same personal scope.
- **Missing handling:** AD-3 defines the scope as `personal(ownerUserId)` or `course(courseId)`, but AD-4 makes the deletion transaction tombstone that scope and advance its generation. The document also offers personal-material deletion with derivative closure. It never distinguishes deleting one lineage root from deleting the owner's entire study scope. A material-level tombstone cannot simply be assumed to exist under this wording.
- **Potential consequence:** Either selective deletion revokes unrelated study data, or an implementation avoids the scope fence and leaves A's in-flight/derived work able to survive or repopulate. The same ambiguity affects shared-scope source cleanup later.
- **Minimum guard:** Keep authorization scope separate from lifecycle targets. Name resource/root tombstones and generations for material deletion, plus account/personal-scope and course-wide deletion as distinct operations. Define descendant closure for multi-parent derivatives and require jobs to check every relevant live root at dispatch/commit. Unrelated B remains available; anything derived from deleted A cannot remain usable merely because B is another parent. Preview the actual closure before confirmation.
- **Later gate evidence:** Epics 1–4/G5 exercise two independent roots, a derivative depending on both, in-flight generation, exports and reminders. Delete A without deleting B or allowing A-derived output to return.

### SEC-03 — Post-removal learner export needs an explicit authorization exception

- **Location:** [AD-3 active enrollment checks](../architecture-shared-technical.md#L60-L64), [AD-4 restricted learner export](../architecture-shared-technical.md#L66-L71), [AD-14 retained controller-restricted history](../architecture-shared-technical.md#L134-L138), [D5 enrollment/export requirement](../../product-policies.md#L61).
- **Trigger condition:** A removed learner requests their own retained course scores/progress.
- **Missing handling:** D5 explicitly preserves that export after removal. The spine requires live enrollment checks for course operations and preserves a narrow export, but does not say how that export remains authorized when ordinary course access ends. A lifecycle exporter, course access service and reporting projection can reasonably interpret the same rules differently.
- **Potential consequence:** The learner loses a promised data control, or an exporter bypasses course authorization too broadly and exposes bank content, other students or full course records.
- **Minimum guard:** Define a separate authenticated self-history-export capability, independent of active enrollment but bound to the requesting learner and retained records. Use a field-allowlisted projection of their scores/progress only, not the ordinary course-content/reporting read path. Define artifact download authorization after removal with the same narrow capability; apply AD-4 expiry, deletion and restore rules. Do not exempt course content, bank data or rosters.
- **Later gate evidence:** Epic 5 integrates removed-learner export with epic 1 lifecycle and epic 3 progress. Export succeeds for the subject while lessons, answer banks, other learners' history and unrelated course data remain denied, including artifact download.

### SEC-04 — DNS validation does not yet bind the source fetch's actual connection

- **Location:** [AD-11 public-source fetch](../architecture-shared-technical.md#L113-L118), [G3](../architecture-shared-technical.md#L282), [source-check execution gate](../source-checks.md#L46).
- **Trigger condition:** A permitted hostname resolves publicly during validation but privately when the HTTP client connects.
- **Missing handling:** Host allowlisting, DNS/IP checks and redirect validation are necessary, but the spine does not require connecting to the vetted address or checking the connected peer. A normal check-then-fetch implementation can resolve DNS again. Every redirect can pass the same preflight and still suffer this check/use race.
- **Potential consequence:** The source-fetch service can reach internal/metadata destinations even while implementing the stated preflight checks, potentially bypassing the intended network trust boundary.
- **Minimum guard:** Make connection-level enforcement part of the shared fetch port: resolve all candidate addresses, reject non-public/forbidden destinations, and pin the validated address through connection establishment while retaining hostname/TLS verification. Reapply policy on redirects and reconnects; an independently enforcing egress proxy/network boundary is an alternative. No credentials or alternate proxy/resolver path may bypass enforcement. Engine/package selection can remain G3 work.
- **Later gate evidence:** G3 includes DNS-rebinding, redirect/reconnect and IPv4/IPv6 destination tests, asserting the actual peer and denied network reachability rather than only URL-validation results.

### SEC-05 — Passive media loading can bypass the provider/fetch privacy boundary

- **Location:** [AD-10 policy-controlled egress](../architecture-shared-technical.md#L106-L111), [AD-11 sanitized rendering](../architecture-shared-technical.md#L113-L118), [AD-12 declarative text/image/media renderers](../architecture-shared-technical.md#L120-L125).
- **Trigger condition:** Uploaded or generated content includes a tracking image/media URL containing private context.
- **Missing handling:** Sanitizing HTML and banning generated executable JavaScript does not prohibit ordinary remote images, media posters, SVG references, styles or other automatic subresource loads. A prompt-injected document can influence a valid declarative image URL; schema-valid output can still trigger a browser request outside AD-10. A server image optimizer/proxy can create an additional fetch path outside AD-11. Instructor preview can leak before approval, and personal study has no instructor gate.
- **Potential consequence:** Private excerpts/identifiers or viewing metadata reach an unapproved processor without opt-in. A naïve optimizer can also reintroduce SSRF despite the dedicated safe source-fetch adapter.
- **Minimum guard:** Specify the renderer's resource-origin policy, not just its markup policy. Learner-visible/preview media should reference scoped registered assets; any remote ingestion must pass the controlled fetch and lifecycle/processing rules. Disallow arbitrary automatic external loads, external SVG/style references and uncontrolled image-optimization fetches; use restrictive CSP and referrer controls as defense in depth. Keep source citations as explicit navigation rather than silently loading third-party resources. This preserves required images/media while closing a non-script injection channel.
- **Later gate evidence:** Epics 2/5/6 verify malicious Markdown, generated image URLs, SVG/media references and pending instructor previews with network interception. No unapproved browser or optimizer request may occur, including when provider consent is declined.
